Dentro scrap

Tutto quello che serve per capire, costruire, provare e modificare scrap: architettura, motore di download multi-segmento, crawler, filtri, HTTP e autenticazione, interfaccia da terminale, test e convenzioni del progetto.

Versione 1.1 Linguaggio Go 1.23 Dimensione ~3.700 righe di Go, più ~900 di test Dipendenze solo golang.org/x/net

Sommario

Premi / per cercare. L'indice analitico elenca file, funzioni e argomenti. I riferimenti file.go:riga puntano alla versione 1.1.

Panoramica

Cos'è scrap visto da dentro, i principi che l'hanno guidato e la mappa del codice.

Cosa copre questo manuale

Il manuale utente spiega cosa fa scrap; questo spiega come. Dopo averlo letto dovresti sapere dove mettere le mani per cambiare il motore di download, il crawler o i filtri senza rompere il resto, e come verificare le modifiche. Si dà per scontato che tu conosca Go e le basi di HTTP. Il perché delle scelte è in decisioni e storia.

Principi

1

Un solo binario

Eseguibile statico (CGO_ENABLED=0) con i certificati radice incorporati: gira anche su un sistema minimo. Unica libreria esterna: il tokenizer HTML di x/net.

⇉

Un motore, due modi

Download diretto e crawl passano dallo stesso Engine: stessi tentativi, stesse barre, stessi filtri.

↺

Mai un file corrotto

Si scrive in .part, sempre in posizione (WriteAt), e si rinomina solo a download completo e controllato.

☑

Buon cittadino del web

User-Agent onesto, robots.txt rispettato, nessun tentativo sugli errori permanenti, Retry-After rispettato.

✓

Test senza rete

32 test ermetici con server HTTP locali, anche sul programma intero (stati di uscita e messaggi).

CI e release

La CI (.github/workflows/ci.yml) gira a ogni push su main e a ogni pull request: installa Go dalla versione di go.mod, esegue make test e make dist, prova il binario Linux e conserva i binari. Su un tag v* un secondo job crea la release GitHub con i due binari e SHA256SUMS; il messaggio del tag annotato diventa la descrizione.

  1. Aggiorna la versione in main.go (appVersion), README.md, docs/index.html e nei due manuali; make per rigenerare ./scrap. make test controlla che tutto coincida.
  2. git tag -a v1.2.0 -m "scrap 1.2.0: …novità…"
  3. git push origin main v1.2.0

Recupero e backup

Il repository è progettato perché un git clone basti a riavere tutto. Il programma pronto è già dentro (./scrap); per ricostruirlo e verificarlo:

$ git clone https://github.com/nic-fio/SCRAPER.git
$ cd SCRAPER && tools/setup-dev.sh --install && make test

tools/setup-dev.sh imposta anche l'identità git locale (nic-fio con l'indirizzo noreply di GitHub), che non viene clonata perché sta in .git/config. tools/backup.sh DIR crea scrap-AAAA-MM-GG.bundle, verificato con git bundle verify, e avvisa se ci sono modifiche non registrate o commit non ancora spinti su GitHub.

Avvio

main (main.go:112) procede così:

  1. wantsHelp intercetta -h, -help, --help, help o l'assenza di argomenti prima di flag.Parse, e mostra la guida.
  2. Definisce le opzioni su un flag.FlagSet con ExitOnError: un'opzione sconosciuta stampa la guida testuale ed esce con 2. Gli alias corto/lungo sono due flag che puntano alla stessa variabile (intVar, strVar, boolVar).
  3. Converte e controlla i valori (main.go:194): dimensioni con parseSize, livello, numeri non negativi, --auth, regex compilate. Ogni errore passa da badArg: messaggio con il nome dell'opzione e stato 2.
  4. Deriva le modalità: --page-requisites senza -r diventa un crawl di profondità 0; -m implica -r e profondità infinita (se -l non è stato dato, o vale 5); in ricorsivo MirrorDirs è sempre vero. Poi le regole di -o (main.go:278).
  5. Crea jar (caricando --load-cookies), client, esegue formLogin se c'è --login-url (errore → stato 1), avvia Progress e l'Engine.
  6. Dopo engine.Run: riepilogo, --save-cookies, e stato 1 se prog.Failed() > 0 (main.go:337).

L'Engine (crawl.go:20) lancia un goroutine per ogni URL accodato; il semaforo sem (capacità -j) limita quanti lavorano insieme e il WaitGroup aspetta anche quelli accodati durante il crawl. visited (protetta da vmu) evita di accodare due volte lo stesso URL (senza frammento). stop() alza un flag atomico che blocca i nuovi accodamenti quando un limite è raggiunto.

Dove va l'output

Barre, messaggi e riepilogo vanno tutti su stderr; su stdout va solo la guida. errf (main.go:97) scrive scrap: …; logf scrive solo con -v. Entrambi passano da gProg.Log quando le barre sono attive, così il messaggio compare sopra l'area viva senza rovinarla. -qa imposta gQuietAll, che zittisce entrambi.

Il motore di download

Sonda, flusso singolo e segmentato, ripresa, tentativi, timeout e limite di banda.

La sonda

probe (download.go:29) fa una GET con Range: bytes=0-0, dentro withRetry:

RispostaSignificato
206Range supportati; dimensione dal totale di Content-Range.
200Range ignorati; dimensione da Content-Length (o −1).
416File vuoto.
altrohttpStatusError con il codice e l'eventuale Retry-After.

Legge e scarta al massimo 64 KB del corpo, così la connessione torna riutilizzabile. Raccoglie anche Content-Type (per i filtri e per riconoscere le pagine HTML) e l'URL finale dopo i redirect.

downloadFile

downloadFile (download.go:73) coordina un file:

  1. Se la destinazione esiste, il file è completo (durante il download si chiama .part): salta, conta come «già presente» ed esce con successo. Vale anche con -c.
  2. Sonda (se non già fatta dal crawler), poi i filtri su dimensione e tipo. Un file scartato non è un errore.
  3. reserveFile: se --max-files è esaurito restituisce errQuota, che ferma il motore senza contare un fallimento.
  4. Sceglie segmented se il server accetta i range, il file è di almeno --min-split e -s > 1; altrimenti singleStream. Entrambi scrivono su DEST.part e rinominano solo a successo.

Download segmentato

segmented (download.go:148) divide il file in -s segmenti uguali (makeSegs; l'ultimo prende il resto), prealloca il .part con Truncate e lancia un goroutine per segmento. Ogni segmento ha i propri tentativi e riparte da start + done; fetchRange scrive con WriteAt e aggiorna i contatori dopo la scrittura, quindi lo stato salvato non è mai avanti rispetto ai dati. Ogni 1,5 secondi, e in caso di errore, lo stato va nel file accanto:

{"url":"https://…","size":5000000,"done":[242176,331528,516704,909200]}

Con -c lo stato viene ricaricato solo se dimensione e numero di segmenti coincidono (altrimenti si riparte da zero). A successo il file di stato viene cancellato e il .part rinominato.

fetchRange pretende una risposta 206: un 200 conterrebbe il file intero, che scritto a partire da from lo corromperebbe. In quel caso restituisce l'errore «il server ha ignorato la richiesta di un pezzo del file» (TestSegmentIgnoringRangeIsRejected).

Flusso singolo

singleStream (download.go:283) tiene in pos il numero di byte realmente scritti:

  • Partenza: con -c e range supportati riparte dalla dimensione del .part esistente (se minore del totale); altrimenti tronca a zero.
  • A ogni tentativo chiede Range: bytes=pos-. Se il server risponde 200 invece di 206, manda il file dall'inizio: si tronca e si riparte da zero.
  • Scrittura posizionale con WriteAt(buf, pos): mai in coda, quindi un tentativo ripetuto non può duplicare dati.
  • Controllo di fine: se la dimensione è nota e lo stream finisce prima, l'errore download incompleto: X/Y byte fa scattare un nuovo tentativo.
Storia

Fino alla 1.0 il file era aperto in accodamento e ogni tentativo ripartiva dall'offset iniziale: dopo una caduta di connessione i dati venivano scritti due volte e il file corrotto veniva rinominato come completo. TestSingleStreamRetryResumesWithoutDuplicates e TestSingleStreamRetryWithoutRangesRestarts falliscono sul codice 1.0 (1.200.000 byte invece di 800.000) e proteggono la correzione.

Tentativi

withRetry (retry.go:79) esegue la funzione fino a 1 + --retries volte:

  • Si ferma subito su errQuota e sugli errori permanenti: isRetryable considera permanenti i 4xx tranne 408 e 429. I 5xx e gli errori di rete sono transitori.
  • Attesa (backoff): se il server ha mandato Retry-After (secondi o data HTTP) lo rispetta; altrimenti --retry-wait raddoppiato a ogni tentativo. Tetto maxBackoff = 60 s, jitter ±20% per non far ripartire insieme tutti i segmenti.

Timeout

--timeout non limita la durata di una richiesta: il client (NewClient, httpclient.go:30) non ha http.Client.Timeout. Il valore vale per:

  • la connessione (net.Dialer.Timeout), l'handshake TLS e l'attesa delle intestazioni di risposta (ResponseHeaderTimeout);
  • il trasferimento fermo: Client.Do avvolge ogni corpo in idleBody, un timer azzerato a ogni lettura che, se scade, annulla il contesto della richiesta. La lettura fallisce con nessun dato ricevuto per …, un errore transitorio: il tentativo successivo riparte dal punto giusto.

Con --timeout 0 tutti questi limiti sono disattivati. Fino alla 1.0 il valore era il timeout totale del client: un segmento più lungo di 60 secondi falliva a ogni tentativo (TestTimeoutDoesNotLimitTotalDuration, TestStalledTransferIsRetried).

Limite di banda

RateLimiter (util.go:75) è un token bucket globale, condiviso da tutti i download, con capacità pari a un secondo di banda. meterReader avvolge ogni corpo di risposta e chiama Take(n) dopo ogni lettura. Take prenota i token anche andando in negativo e dorme in proporzione al deficit: così più segmenti in attesa sommano l'attesa invece di moltiplicare la banda (era un bug della prima versione, vedi la storia). parseSize accetta un numero, anche decimale, con suffisso k/M/G/T (potenze di 1024) ed eventuale B.

Il crawler

Come vengono esplorate le pagine, estratti i link e salvati i file.

Accodamento ed esplorazione

enqueue(url, depth, req) (crawl.go:130) toglie il frammento, deduplica su visited, applica allowCrawl e robots.txt e lancia il goroutine. process fa la sonda e decide:

  • HTML (text/html o application/xhtml), depth ≤ livello, non requisito → crawlHTML;
  • altrimenti → filtro di estensione e downloadFile (una pagina HTML scaricata così, per esempio un iframe come requisito, prende comunque l'estensione .html).

crawlHTML (crawl.go:192) scarica la pagina intera in memoria (massimo 32 MB), calcola la destinazione dall'URL finale e, se un'altra pagina è già finita nello stesso file (pagesSeen: per esempio / e /index.html), si ferma. Altrimenti salva la pagina se passa allowSaveHTML, estrae i link e accoda: tutti a depth+1 se depth < livello; all'ultimo livello, con --page-requisites, solo i requisiti con req=true, che ignorano profondità e --no-parent e non vengono esplorati.

Ogni pagina costa quindi due richieste: la sonda e la GET completa.

Estrazione dei link

extractPageLinks (crawl.go:301) usa il tokenizer di golang.org/x/net/html, tollerante all'HTML malformato. Raccoglie href, src, poster, le voci di srcset, gli url(…) negli attributi style e nei blocchi <style>; rispetta <base href>; scarta #…, javascript:, mailto:, data:, tel: e tutto ciò che non è http/https. Il testo di <script> non viene letto (niente falsi positivi da stringhe JavaScript).

Restituisce due elenchi: tutti i link e i requisiti. Sono link di navigazione solo gli href di <a>, <area> e dei <link> che non sono risorse (isRequisiteRel: stylesheet, icon, apple-touch-icon, preload, modulepreload, manifest); tutto il resto è requisito.

Da URL a file

localPath (crawl.go:434):

  1. parte dal percorso decodificato; vuoto o finale / → index.html;
  2. la query si aggiunge dopo @ (/scarica?id=4 → scarica@id_4);
  3. per le pagine HTML aggiunge .html se l'estensione non è .html, .htm o .xhtml;
  4. sostituisce con _ ogni carattere fuori da [A-Za-z0-9._-/] (reUnsafe): niente spazi, accenti o caratteri speciali nei nomi, e nessun .. può uscire dalla cartella perché il percorso è ripulito da filepath.Join;
  5. con MirrorDirs (-r/-m) il file va in DIR/host/percorso (l'host senza porta); altrimenti in DIR/ con il solo nome.

Conversione dei link

convertLinks (crawl.go:471) gira alla fine, sulle pagine salvate. Con reAbsURL trova gli indirizzi assoluti interi (fino a spazio, virgolette, parentesi o <>), toglie il frammento, cerca l'indirizzo (anche con le entità &amp; decodificate) tra quelli scaricati e lo sostituisce con il percorso relativo, rimettendo il frammento. Gli indirizzi non scaricati restano assoluti; i link già relativi restano com'erano, perché le cartelle ricalcano il sito.

Fino alla 1.0 la sostituzione era testuale, con strings.ReplaceAll in ordine casuale: l'indirizzo della home poteva alterare quelli più lunghi (https://sito/img/a.png → index.htmlimg/a.png). Lo protegge TestConvertLinksWholeURLsOnly.

robots.txt

allowedByRobots (robots.go:21) scarica /robots.txt una volta per schema+host e lo tiene in memoria. Considera solo il gruppo User-agent: *; le regole Allow/Disallow sono prefissi, vince la più lunga e a parità vince Allow. Un robots.txt assente, non 200 o irraggiungibile vuol dire «tutto permesso». Vale solo per enqueue, cioè in modalità ricorsiva.

HTTP, autenticazione e cookie

Come vengono costruite le richieste, gestiti gli accessi e conservate le sessioni.

Le richieste

newRequest (httpclient.go:50) imposta, in quest'ordine: User-Agent, Referer, le intestazioni di -H, Authorization: Bearer, Cookie di --cookie, e l'autenticazione Basic preventiva (se c'è --user, non c'è un token e --auth non è digest). Lo User-Agent normale è scrap/1.1 (+https://github.com/nic-fio/SCRAPER) (defaultUserAgent, main.go:29): onesto e contattabile, come fanno i bot ben educati. Il client segue i redirect (fino a 10, comportamento di Go), usa i proxy delle variabili d'ambiente e HTTP/2 quando il server lo offre.

Digest

Client.Do riconosce un 401 con WWW-Authenticate: Digest: ricostruisce la richiesta (cloneForRetry, conservando il Range) e la ripete con l'intestazione calcolata da digestHeader (MD5 o MD5-sess, qop=auth, contatore nc atomico, cnonce casuale). parseChallenge gestisce le virgole tra virgolette.

Login da modulo

formLogin (httpclient.go:253) invia --login-data così com'è, in POST application/x-www-form-urlencoded, con User-Agent e intestazioni -H. I cookie di risposta (e dei redirect) finiscono nel jar condiviso. Un codice ≥ 400 è un errore fatale. Non legge prima la pagina di login, quindi non conosce eventuali token anti-CSRF.

Cookie jar

Jar (cookies.go:17) implementa http.CookieJar: dominio (con o senza host-only), percorso, Secure, scadenza (Max-Age ha la precedenza su Expires; un cookie scaduto cancella quello esistente). Load e Save usano il formato Netscape a 7 colonne separate da tabulazioni; le righe #HttpOnly_ vengono lette.

Certificati

roots.go incorpora cacerts.pem con go:embed e lo registra con x509.SetFallbackRoots: Go lo usa solo se il sistema non ha un proprio archivio di certificati (container minimi, sistemi senza ca-certificates). Sui sistemi normali restano prioritari i certificati del sistema, che ricevono gli aggiornamenti. Per aggiornare il pacchetto: curl -fsSL -o cacerts.pem https://curl.se/ca/cacert.pem. --insecure imposta InsecureSkipVerify per tutto il client.

Barre di avanzamento

Come vengono disegnate le barre senza rovinarle con i messaggi.

Progress (progress.go) tiene l'elenco dei file in corso e i contatori atomici: byte, file fatti, indirizzi falliti (fail, chiamato da handleErr e per i seed non validi), file già presenti (skipped). Se stderr è un terminale e l'uscita non è silenziata, run ridisegna ogni 120 ms l'area viva: una riga per file (al massimo maxBars = 6), la riga dei segmenti (▰▱) per i download a più connessioni, un separatore e il piede «attivi · fatti · falliti · byte · velocità». Per ridisegnare risale di liveLines-1 righe (ESC[nA), cancella fino in fondo (ESC[J) e riscrive.

La velocità è una media mobile esponenziale (0,6 × precedente + 0,4 × istantanea). La barra usa gli ottavi di blocco Unicode per la frazione. Senza terminale non ci sono barre: i messaggi sono righe semplici. Con -qe/-qa Progress è quiet: niente barre, righe ✓ né riepilogo; restano solo i messaggi di errf (che -qa zittisce).

finish scrive il riepilogo: ✓ (o ✗ se qualcosa è fallito), file, falliti, già presenti, byte, durata, media.

Guida e interfaccia

Una sola fonte per il testo della guida, tre modi di mostrarla.

Il contenuto della guida sta in help.go: helpSections (le opzioni per sezione), helpExamples, descrizione. Da lì nascono sia la pagina di manuale (buildHelp, con colori ANSI) sia le schede della TUI (buildTabs). tools/check-docs.py verifica che ogni opzione definita in main.go compaia in helpSections e nel manuale utente.

displayHelp sceglie:

  1. stdin o stdout non sono terminali → testo semplice senza colori su stdout;
  2. altrimenti la TUI (runTUI); se fallisce (terminale sotto 44×10, o sistema diverso da Linux) →
  3. pagina a colori nel pager: $PAGER, oppure less -R -F -X, oppure more, oppure stampata così com'è.

La TUI (tui.go) usa lo schermo alternativo (ESC[?1049h), nasconde il cursore e mette stdin in raw mode con ioctl TCGETS/TCSETS (term_linux.go). Un goroutine legge i byte e parseKeys li traduce tutti in eventi (una lettura può contenere più tasti o una sequenza di escape; leggerne solo il primo bloccava la TUI in una versione iniziale). Un ESC isolato vale come uscita. SIGWINCH ridisegna alla nuova dimensione; SIGTERM/SIGHUP escono ripristinando il terminale. Il progetto gemello hoster ha ripreso queste parti.

Test

Cosa è coperto, come si esegue, e i controlli della documentazione.

La suite

32 test ermetici: nessuna rete reale. I server sono httptest locali che imitano file con e senza range, cadute di connessione a metà, server bloccati, server lenti, siti con pagine, robots.txt e link rotti. Girano con -race perché segmenti, crawl e barre sono concorrenti.

Provare il programma intero

main_test.go usa lo stesso eseguibile di test come programma: TestMain, se trova SCRAP_TEST_MAIN=1, sostituisce os.Args con gli argomenti dopo -- e chiama main(). runScrap lancia il sottoprocesso e restituisce stato di uscita e uscita. Così si verificano os.Exit, messaggi e silenzio senza compilare un binario a parte.

Controlli della documentazione

tools/check-docs.py, eseguito da make test e quindi dalla CI, fallisce se:

  • un'opzione di helpSections non ha la sua voce nel riferimento del manuale utente (data-index di un <dt>), o il manuale documenta un'opzione che non esiste;
  • un'opzione definita in main.go non compare nella guida integrata;
  • un file .go manca dalla mappa dei file, o il numero di righe indicato si scosta di più del 10% da quello vero;
  • l'eseguibile ./scrap manca, non è un ELF x86-64 o non contiene la versione di main.go (segno che non è stato rigenerato dopo un cambio di versione);
  • la versione di main.go non coincide con quella di README.md, docs/index.html e dei due manuali;
  • un link interno #ancora dei manuali punta a un id che non esiste.

Convenzioni

Come si scrive codice e testo in questo progetto.

  • Tutto in italiano: messaggi, commenti, documentazione. I testi rivolti all'utente sono semplici, senza gergo tecnico.
  • Formato: gofmt; go vet pulito.
  • Nessuna nuova dipendenza senza una ragione forte: il binario unico è una scelta di progetto.
  • Ogni correzione ha il suo test di regressione, con un server locale, e il test deve fallire sul codice prima della correzione.
  • Mai scrivere in coda in un file di download: sempre WriteAt a una posizione nota.
  • Opzioni sbagliate → badArg (stato 2, nome dell'opzione nel messaggio), mai MustCompile o valori ignorati in silenzio.
  • La documentazione si aggiorna insieme al codice: nuova opzione → riga in helpSections e voce nel riferimento del manuale utente; nuovo file → riga nella mappa.

Limiti noti e punti aperti

Comportamenti noti, da correggere o da tenere presenti, e idee per il futuro.

Limiti noti

DoveComportamentoEffetto
download.go:148Stato di ripresa e dati non vengono forzati su disco (fsync). Dopo uno spegnimento improvviso lo stato può dire più byte di quelli arrivati sul disco: il file ripreso avrebbe dei buchi. Con Ctrl+C non succede.
crawl.go:130Un goroutine per ogni URL accodato; visited non si svuota mai. Su siti enormi (centinaia di migliaia di URL) cresce la memoria.
crawl.go:192Pagine lette interamente in memoria, al massimo 32 MB; due richieste per pagina. Una pagina più grande viene troncata; un crawl costa il doppio delle richieste strettamente necessarie.
crawl.go:434Il nome della cartella è l'host senza porta; i caratteri non ASCII diventano _. Due server sullo stesso host con porte diverse finiscono nella stessa cartella; nomi diversi possono coincidere dopo la sostituzione (il secondo viene saltato come già presente).
robots.goSolo il gruppo User-agent: *, solo prefissi. Non gestisce i caratteri jolly * e $ né Crawl-delay.
httpclient.go:253Il login da modulo non legge prima la pagina. I siti con token anti-CSRF rifiutano il login: servono i cookie esportati dal browser.
cookies.go:44Il dominio dichiarato da un cookie non viene confrontato con l'host che lo imposta. Un sito potrebbe impostare cookie per un altro dominio durante un crawl con --span-hosts.
filter.go:172La quota è controllata dopo ogni scrittura, da download paralleli. Il totale può superare --quota di qualche blocco per ogni download attivo.
main.goPassword e token passano come argomenti. Restano nella cronologia della shell e sono visibili in ps durante l'esecuzione.

Corretti nella 1.1

Per confronto con la 1.0 (ogni punto ha il suo test): flusso singolo che duplicava i dati a ogni nuovo tentativo; --timeout come durata massima della richiesta; segmento servito con 200 scritto nel punto sbagliato; -c che riscaricava i file completi; stato 0 anche con download falliti; crash con una regex sbagliata; dimensioni e livello sbagliati ignorati; -j 0 che mandava in crash il programma (stallo di tutti i goroutine); -qe e -qa non silenziosi; -o con più indirizzi; --page-requisites senza effetto; pagina salvata due volte nel mirror; --convert-links che alterava gli indirizzi più lunghi; seed non valido segnalato due volte dopo un minuto di tentativi inutili.

Idee per il futuro

  • fsync di dati e stato a intervalli, per una ripresa sicura anche dopo uno spegnimento.
  • Una coda con un numero fisso di goroutine al posto di un goroutine per URL.
  • Caratteri jolly e Crawl-delay in robots.txt.
  • Login da modulo che legge prima la pagina e riprende i campi nascosti.
  • Proxy SOCKS, deduplicazione per impronta, statistiche in JSON (candidati v2 del diario di sviluppo).

Glossario

Richiesta Range
Richiesta HTTP di una parte del file (bytes=da-a); risposta 206 se supportata.
Seed
Un indirizzo di partenza, dato sulla riga di comando o con -i.
Requisito di pagina
Una risorsa che serve a mostrare una pagina: immagine, foglio di stile, script, icona, iframe.
Backoff con jitter
Attesa tra i tentativi che cresce a ogni fallimento, con una piccola variazione casuale perché più connessioni non ripartano tutte nello stesso istante.
Token bucket
Limitatore di banda: un secchio di «gettoni» (byte) che si riempie alla velocità consentita; ogni lettura ne consuma.
Formato Netscape
Il formato testuale dei file cookies.txt, esportabile dai browser.
Git bundle
Un file che contiene un repository git completo, clonabile senza rete.
