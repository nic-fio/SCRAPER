    Chapter 1

    Overview

    What scrap is, seen from the inside, the principles that guided it and the map of the code.

    Press / to search. The index lists files, functions and topics. The file.go:line references point to version 1.1.

    1.1 · What this manual covers

    The user manual explains what scrap does; this one explains how. After reading it you should know where to put your hands to change the download engine, the crawler or the filters without breaking the rest, and how to verify your changes. It assumes you know Go and the basics of HTTP. The why behind the choices is in decisions and history.

    1.2 · Principles

    1.3 · File map

    The whole program is a single package main. The line counts are checked by tools/check-docs.py: if a file changes length by more than 10%, or a new one appears without a row here, make test fails.

    Chapter 2

    Repository and tools

    How the repository is organized, and how it is built, tested and published.

    2.1 · Structure

    !
    Personal files. Cookie files (cookies.txt, cj.txt, *.cookies) contain open sessions and are in .gitignore, like the downloads (*.part, *.iso, *.bin…) and dist/. The repository is public: never git add -A without looking.

    2.2 · Build

    $ tools/setup-dev.sh --install
$ make
$ make test
$ make dist

    go.mod requires Go 1.23 (at least 1.22 is needed for math/rand/v2); on Debian 13 the package golang-go is 1.24. With an older Go, but at least 1.21, the directive automatically downloads the right toolchain. The first build downloads golang.org/x/net into the module cache.

    2.3 · CI and releases

    The CI (.github/workflows/ci.yml) runs on every push to main and on every pull request: it installs Go at the version in go.mod, runs make test and make dist, tries out the Linux binary and keeps the binaries. On a v* tag a second job creates the GitHub release with the two binaries and SHA256SUMS; the message of the annotated tag becomes the description.

    1. Update the version in main.go (appVersion), README.md, docs/index.html and in the two manuals; make to regenerate ./scrap. make test checks that everything matches.
    2. git tag -a v1.2.0 -m "scrap 1.2.0: …novità…"
    3. git push origin main v1.2.0

    2.4 · Recovery and backup

    The repository is designed so that a git clone is enough to get everything back. The ready-made program is already inside (./scrap); to rebuild and verify it:

    $ git clone https://github.com/nic-fio/SCRAPER.git
$ cd SCRAPER && tools/setup-dev.sh --install && make test

    tools/setup-dev.sh also sets the local git identity (nic-fio with GitHub's noreply address), which is not cloned because it lives in .git/config. tools/backup.sh DIR creates scrap-YYYY-MM-DD.bundle, verified with git bundle verify, and warns if there are uncommitted changes or commits not yet pushed to GitHub.

    Chapter 3

    Architecture

    The components, how they talk to each other and what happens during a run.

    3.1 · Components

    3.2 · Startup

    main (main.go:112) proceeds as follows:

    1. wantsHelp intercepts -h, -help, --help, help or the absence of arguments before flag.Parse, and shows the help.
    2. Defines the options on a flag.FlagSet with ExitOnError: an unknown option prints the text help and exits with 2. The short/long aliases are two flags that point to the same variable (intVar, strVar, boolVar).
    3. Converts and validates the values (main.go:194): sizes with parseSize, level, non-negative numbers, --auth, compiled regexes. Every error goes through badArg: a message with the name of the option and status 2.
    4. Derives the modes: --page-requisites without -r becomes a crawl of depth 0; -m implies -r and infinite depth (if -l was not given, or is 5); in recursive mode MirrorDirs is always true. Then the rules for -o (main.go:278).
    5. Creates the jar (loading --load-cookies) and the client, runs formLogin if there is --login-url (error → status 1), starts Progress and the Engine.
    6. After engine.Run: summary, --save-cookies, and status 1 if prog.Failed() > 0 (main.go:337).

    3.3 · A run

    The Engine (crawl.go:20) launches one goroutine for every queued URL; the semaphore sem (capacity -j) limits how many work at the same time and the WaitGroup also waits for those queued during the crawl. visited (protected by vmu) avoids queuing the same URL twice (without the fragment). stop() raises an atomic flag that blocks new queuing when a limit has been reached.

    3.4 · Where the output goes

    Bars, messages and summary all go to stderr; only the help goes to stdout. errf (main.go:97) writes scrap: …; logf writes only with -v. Both go through gProg.Log when the bars are active, so the message appears above the live area without spoiling it. -qa sets gQuietAll, which silences both.

    Chapter 4

    The download engine

    Probe, single and segmented stream, resume, retries, timeouts and bandwidth limit.

    4.1 · The probe

    probe (download.go:29) makes a GET with Range: bytes=0-0, inside withRetry:

    It reads and discards at most 64 KB of the body, so that the connection becomes reusable again. It also collects Content-Type (for the filters and to recognize HTML pages) and the final URL after the redirects.

    4.2 · downloadFile

    downloadFile (download.go:73) coordinates one file:

    1. If the destination exists, the file is complete (during the download it is called .part): it skips it, counts it as «already present» and exits successfully. This applies with -c too.
    2. Probe (if the crawler has not already done it), then the filters on size and type. A discarded file is not an error.
    3. reserveFile: if --max-files is used up it returns errQuota, which stops the engine without counting a failure.
    4. Chooses segmented if the server accepts ranges, the file is at least --min-split and -s > 1; otherwise singleStream. Both write to DEST.part and rename only on success.

    4.3 · Segmented download

    segmented (download.go:148) splits the file into -s equal segments (makeSegs; the last one takes the remainder), preallocates the .part with Truncate and launches one goroutine per segment. Each segment has its own retries and restarts from start + done; fetchRange writes with WriteAt and updates the counters after the write, so the saved state is never ahead of the data. Every 1.5 seconds, and in case of error, the state goes into the file next to it:

    {"url":"https://…","size":5000000,"done":[242176,331528,516704,909200]}

    With -c the state is reloaded only if the size and the number of segments match (otherwise it starts again from zero). On success the state file is deleted and the .part renamed.

    fetchRange insists on a 206 response: a 200 would contain the whole file, which, written starting from from, would corrupt it. In that case it returns the error «il server ha ignorato la richiesta di un pezzo del file» (the server ignored the request for a piece of the file) (TestSegmentIgnoringRangeIsRejected).

    4.4 · Single stream

    singleStream (download.go:283) keeps in pos the number of bytes actually written:

    • Start: with -c and ranges supported it restarts from the size of the existing .part (if smaller than the total); otherwise it truncates to zero.
    • At every attempt it asks for Range: bytes=pos-. If the server answers 200 instead of 206, it is sending the file from the beginning: the file is truncated and restarts from zero.
    • Positional writing with WriteAt(buf, pos): never appending, so a repeated attempt cannot duplicate data.
    • End check: if the size is known and the stream ends early, the error download incompleto: X/Y byte triggers a new attempt.
    !
    History. Up to 1.0 the file was opened in append mode and every attempt restarted from the initial offset: after a dropped connection the data was written twice and the corrupted file was renamed as complete. TestSingleStreamRetryResumesWithoutDuplicates and TestSingleStreamRetryWithoutRangesRestarts fail on the 1.0 code (1,200,000 bytes instead of 800,000) and protect the fix.

    4.5 · Retries

    withRetry (retry.go:79) runs the function up to 1 + --retries times:

    • It stops immediately on errQuota and on permanent errors: isRetryable considers 4xx permanent except 408 and 429. 5xx and network errors are transient.
    • Wait (backoff): if the server sent Retry-After (seconds or an HTTP date) it respects it; otherwise --retry-wait doubled at every attempt. Cap maxBackoff = 60 s, jitter ±20% so that all the segments do not restart together.

    4.6 · Timeouts

    --timeout does not limit the duration of a request: the client (NewClient, httpclient.go:30) has no http.Client.Timeout. The value applies to:

    • the connection (net.Dialer.Timeout), the TLS handshake and the wait for the response headers (ResponseHeaderTimeout);
    • a stalled transfer: Client.Do wraps every body in idleBody, a timer reset at every read which, if it expires, cancels the request's context. The read fails with nessun dato ricevuto per … (no data received for …), a transient error: the next attempt restarts from the right point.

    With --timeout 0 all these limits are disabled. Up to 1.0 the value was the client's total timeout: a segment longer than 60 seconds failed at every attempt (TestTimeoutDoesNotLimitTotalDuration, TestStalledTransferIsRetried).

    4.7 · Bandwidth limit

    RateLimiter (util.go:75) is a global token bucket, shared by all downloads, with a capacity equal to one second of bandwidth. meterReader wraps every response body and calls Take(n) after every read. Take reserves the tokens even when going negative and sleeps in proportion to the deficit: that way several waiting segments add up their waits instead of multiplying the bandwidth (this was a bug in the first version, see the history). parseSize accepts a number, decimals included, with the suffix k/M/G/T (powers of 1024) and an optional B.

    Chapter 5

    The crawler

    How pages are explored, links extracted and files saved.

    5.1 · Queuing and exploration

    enqueue(url, depth, req) (crawl.go:130) removes the fragment, deduplicates on visited, applies allowCrawl and robots.txt and launches the goroutine. process runs the probe and decides:

    • HTML (text/html or application/xhtml), depth ≤ level, not a requisite → crawlHTML;
    • otherwise → extension filter and downloadFile (an HTML page downloaded this way, for example an iframe as a requisite, still gets the .html extension).

    crawlHTML (crawl.go:192) downloads the whole page into memory (32 MB at most), computes the destination from the final URL and, if another page has already ended up in the same file (pagesSeen: for example / and /index.html), stops. Otherwise it saves the page if it passes allowSaveHTML, extracts the links and queues them: all at depth+1 if depth < level; at the last level, with --page-requisites, only the requisites with req=true, which ignore depth and --no-parent and are not explored.

    Each page therefore costs two requests: the probe and the full GET.

    5.2 · Link extraction

    extractPageLinks (crawl.go:301) uses the tokenizer from golang.org/x/net/html, which tolerates malformed HTML. It collects href, src, poster, the entries of srcset, the url(…) in style attributes and in <style> blocks; it respects <base href>; it discards #…, javascript:, mailto:, data:, tel: and everything that is not http/https. The text of <script> is not read (no false positives from JavaScript strings).

    It returns two lists: all the links and the requisites. Only these are navigation links: the href of <a>, <area> and of the <link> elements that are not resources (isRequisiteRel: stylesheet, icon, apple-touch-icon, preload, modulepreload, manifest); everything else is a requisite.

    5.3 · From URL to file

    localPath (crawl.go:434):

    1. starts from the decoded path; empty or ending in / → index.html;
    2. the query is appended after @ (/scarica?id=4 → scarica@id_4);
    3. for HTML pages it appends .html if the extension is not .html, .htm or .xhtml;
    4. replaces with _ every character outside [A-Za-z0-9._-/] (reUnsafe): no spaces, accents or special characters in the names, and no .. can escape from the folder because the path is cleaned up by filepath.Join;
    5. with MirrorDirs (-r/-m) the file goes into DIR/host/path (the host without the port); otherwise into DIR/ with just its name.

    5.4 · Link conversion

    convertLinks (crawl.go:471) runs at the end, on the saved pages. With reAbsURL it finds whole absolute addresses (up to a space, quote, parenthesis or <>), removes the fragment, looks up the address (also with the &amp; entities decoded) among the downloaded ones and replaces it with the relative path, putting the fragment back. Addresses that were not downloaded stay absolute; links that are already relative stay as they were, because the folders mirror the site.

    Up to 1.0 the replacement was textual, with strings.ReplaceAll in random order: the address of the home page could alter longer ones (https://sito/img/a.png → index.htmlimg/a.png). TestConvertLinksWholeURLsOnly protects against this.

    5.5 · robots.txt

    allowedByRobots (robots.go:21) downloads /robots.txt once per scheme+host and keeps it in memory. It considers only the User-agent: * group; the Allow/Disallow rules are prefixes, the longest wins and on a tie Allow wins. A robots.txt that is missing, not 200 or unreachable means «everything allowed». It applies only to enqueue, that is in recursive mode.

    Chapter 6

    The filters

    Which filter applies at which moment.

    If neither --span-hosts nor --domains is given, Run copies the seed hosts into domains: the crawl stays on the starting hosts and their subdomains (hostInList accepts host == d or the suffix .d). In direct download, without -r, only the filters from the third one down apply.

    Chapter 7

    HTTP, authentication and cookies

    How requests are built, access is handled and sessions are kept.

    7.1 · Requests

    newRequest (httpclient.go:50) sets, in this order: User-Agent, Referer, the headers from -H, Authorization: Bearer, the Cookie from --cookie, and preemptive Basic authentication (if there is --user, there is no token and --auth is not digest). The default User-Agent is scrap/1.1 (+https://github.com/nic-fio/SCRAPER) (defaultUserAgent, main.go:29): honest and contactable, as well-behaved bots do. The client follows redirects (up to 10, Go's behavior), uses the proxies from the environment variables and HTTP/2 when the server offers it.

    7.2 · Digest

    Client.Do recognizes a 401 with WWW-Authenticate: Digest: it rebuilds the request (cloneForRetry, keeping the Range) and repeats it with the header computed by digestHeader (MD5 or MD5-sess, qop=auth, atomic nc counter, random cnonce). parseChallenge handles commas inside quotes.

    7.3 · Form login

    formLogin (httpclient.go:253) sends --login-data as it is, as a POST application/x-www-form-urlencoded, with the User-Agent and the -H headers. The cookies from the response (and from the redirects) end up in the shared jar. A code ≥ 400 is a fatal error. It does not read the login page first, so it does not know about any anti-CSRF tokens.

    7.4 · Cookie jar

    Jar (cookies.go:17) implements http.CookieJar: domain (with or without host-only), path, Secure, expiry (Max-Age takes precedence over Expires; an expired cookie deletes the existing one). Load and Save use the Netscape format with 7 tab-separated columns; #HttpOnly_ lines are read.

    7.5 · Certificates

    roots.go embeds cacerts.pem with go:embed and registers it with x509.SetFallbackRoots: Go uses it only if the system has no certificate store of its own (minimal containers, systems without ca-certificates). On normal systems the system's certificates, which receive updates, keep priority. To update the bundle: curl -fsSL -o cacerts.pem https://curl.se/ca/cacert.pem. --insecure sets InsecureSkipVerify for the whole client.

    Chapter 8

    Progress bars

    How the bars are drawn without being spoiled by the messages.

    Progress (progress.go) keeps the list of files in progress and the atomic counters: bytes, files done, failed addresses (fail, called by handleErr and for invalid seeds), files already present (skipped). If stderr is a terminal and the output is not silenced, run redraws the live area every 120 ms: one line per file (at most maxBars = 6), the segment line (▰▱) for multi-connection downloads, a separator and the footer «active · done · failed · bytes · speed». To redraw it moves up liveLines-1 lines (ESC[nA), clears to the end (ESC[J) and writes again.

    The speed is an exponential moving average (0.6 × previous + 0.4 × instantaneous). The bar uses Unicode eighth blocks for the fraction. Without a terminal there are no bars: the messages are plain lines. With -qe/-qa Progress is quiet: no bars, no ✓ lines and no summary; only the errf messages remain (which -qa silences).

    finish writes the summary: ✓ (or ✗ if something failed), files, failed, already present, bytes, duration, average.

    Chapter 9

    Help and interface

    A single source for the help text, three ways of showing it.

    The content of the help lives in help.go: helpSections (the options by section), helpExamples, descrizione. From there come both the manual page (buildHelp, with ANSI colors) and the TUI tabs (buildTabs). tools/check-docs.py verifies that every option defined in main.go appears in helpSections and in the user manual.

    displayHelp chooses:

    1. stdin or stdout are not terminals → plain text without colors on stdout;
    2. otherwise the TUI (runTUI); if it fails (terminal smaller than 44×10, or a system other than Linux) →
    3. color page in the pager: $PAGER, or less -R -F -X, or more, or printed as it is.

    The TUI (tui.go) uses the alternate screen (ESC[?1049h), hides the cursor and puts stdin in raw mode with the ioctls TCGETS/TCSETS (term_linux.go). A goroutine reads the bytes and parseKeys translates all of them into events (a single read can contain several keys or an escape sequence; reading only the first one froze the TUI in an early version). A lone ESC counts as quitting. SIGWINCH redraws at the new size; SIGTERM/SIGHUP quit, restoring the terminal. The sister project hoster has reused these parts.

    Chapter 10

    Tests

    What is covered, how to run it, and the documentation checks.

    10.1 · The suite

    32 hermetic tests: no real network. The servers are local httptest servers that imitate files with and without ranges, connections dropping halfway, stalled servers, slow servers, sites with pages, robots.txt and broken links. They run with -race because segments, crawl and bars are concurrent.

    10.2 · Testing the whole program

    main_test.go uses the test executable itself as the program: TestMain, if it finds SCRAP_TEST_MAIN=1, replaces os.Args with the arguments after -- and calls main(). runScrap launches the subprocess and returns the exit status and the output. This way os.Exit, messages and silence are verified without compiling a separate binary.

    10.3 · Documentation checks

    tools/check-docs.py, run by make test and therefore by the CI, fails if:

    • an option in helpSections does not have its entry in the user manual's reference (data-index of a <dt>), or the manual documents an option that does not exist;
    • an option defined in main.go does not appear in the built-in help;
    • a .go file is missing from the file map, or the number of lines stated differs by more than 10% from the real one;
    • the executable ./scrap is missing, is not an x86-64 ELF or does not contain the version from main.go (a sign that it was not regenerated after a version change);
    • the version in main.go does not match the one in README.md, docs/index.html and the two manuals;
    • an internal #anchor link in the manuals points to an id that does not exist, or a link to a local page points to a file that does not exist.
    Chapter 11

    Conventions

    How code and text are written in this project.

    • Program in Italian, manuals in English: messages, comments and the built-in help are in Italian; the two HTML manuals are in English. Texts aimed at the user are simple, without technical jargon.
    • Formatting: gofmt; clean go vet.
    • No new dependencies without a strong reason: the single binary is a design choice.
    • Every fix has its own test, a regression test with a local server, and the test must fail on the code before the fix.
    • Never append to a download file: always WriteAt at a known position.
    • Wrong options → badArg (status 2, name of the option in the message), never MustCompile or values silently ignored.
    • Documentation is updated together with the code: new option → a line in helpSections and an entry in the user manual's reference; new file → a row in the map.
    Chapter 12

    Known limitations and open issues

    Known behaviors, to be fixed or kept in mind, and ideas for the future.

    12.1 · Known limitations

    12.2 · Fixed in 1.1

    For comparison with 1.0 (every item has its own test): single stream that duplicated the data at every new attempt; --timeout as the maximum duration of the request; segment served with 200 written at the wrong place; -c that downloaded complete files again; status 0 even with failed downloads; crash with a wrong regex; wrong sizes and levels ignored; -j 0 that crashed the program (all goroutines deadlocked); -qe and -qa not silent; -o with several addresses; --page-requisites with no effect; page saved twice in the mirror; --convert-links that altered longer addresses; invalid seed reported twice after a minute of useless retries.

    12.3 · Ideas for the future

    • fsync of data and state at intervals, for a safe resume even after a power-off.
    • A queue with a fixed number of goroutines instead of one goroutine per URL.
    • Wildcards and Crawl-delay in robots.txt.
    • Form login that reads the page first and picks up the hidden fields.
    • SOCKS proxy, deduplication by hash, statistics in JSON (v2 candidates from the development log).
    Chapter 13

    Glossary

    Range request
    HTTP request for part of the file (bytes=from-to); response 206 if supported.
    Seed
    A starting address, given on the command line or with -i.
    Page requisite
    A resource needed to display a page: image, style sheet, script, icon, iframe.
    Backoff with jitter
    A wait between attempts that grows with every failure, with a small random variation so that several connections do not all restart at the same instant.
    Token bucket
    Bandwidth limiter: a bucket of «tokens» (bytes) that fills up at the permitted speed; every read uses some up.
    Netscape format
    The text format of cookies.txt files, which can be exported from browsers.
    Git bundle
    A file that contains a complete git repository, which can be cloned without a network.
